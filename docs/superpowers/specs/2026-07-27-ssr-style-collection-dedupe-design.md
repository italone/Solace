# SSR Style Collection And Hydration Deduplication Design

## Goal

Add a single style-registration path that works for any Solace render tree, not just `.solace`
components. On the server, styles registered during `renderToString()` should be collected and
returned with the HTML. On the client, `mount()` and `hydrate()` should reuse existing
`style[data-s-id]` tags instead of injecting duplicates.

This is a runtime contract change, not a syntax expansion. `.solace` stays within the current narrow
surface.

## Context

Solace now has:

- `renderToString()` in `@italone/solace/server`.
- `createApp(App).hydrate(container)` in the root package.
- `.solace` compilation that currently injects scoped styles directly with DOM code.
- No public runtime style registry yet.

The current compiler output assumes browser globals and appends a `<style>` tag in generated client
code. That works for client rendering, but it cannot participate in server-side collection or
hydration dedupe.

## Proposed Public API

Add a root-package runtime helper:

```ts
import { useStyle } from "@italone/solace";

useStyle(scopeId, css);
```

Semantics:

- `scopeId` identifies the logical style block.
- `css` is the scoped stylesheet text.
- The call is valid only while Solace is rendering a component tree.
- Repeated registrations of the same `scopeId` and identical `css` are deduped.
- Repeated registrations of the same `scopeId` with different `css` are rejected as a conflict.

This helper is the single registration path for:

- `.solace` scoped styles generated by the compiler.
- Hand-authored components or utilities that want the same SSR/hydration behavior.

## Style Data Model

The server renderer should treat registered styles as serialized HTML blocks, not raw CSS strings.
`RenderToStringResult.styles` remains an ordered `string[]`, but each entry is a complete
`<style data-s-id="...">...</style>` string.

That keeps the return shape simple for SSG and shell code while carrying the `scopeId` needed for
hydration dedupe.

Order rules:

- Preserve first encounter order.
- Collapse duplicate registrations of the same `scopeId` and identical `css`.
- Reject conflicting registrations of the same `scopeId` and different `css`.

## Server Rendering Flow

`renderToString()` should install a request-scoped style collector before rendering the root VNode or
component. During component setup/render, `useStyle()` writes into that collector.

The collector is owned by the current `renderToString()` call, so styles do not leak between
requests.

At the end of the render:

- HTML is returned as before.
- `styles` contains serialized style tags for the current request.
- SSG can inject those tags directly into its shell output.

This applies to any render tree, not just SFC-generated components.

## Client Runtime Flow

`mount()` and `hydrate()` should share the same style sink.

On the client:

- Before the first style registration, initialize a document-level registry from existing
  `style[data-s-id]` tags.
- If `useStyle()` sees an already-present `scopeId` with the same `css`, it no-ops.
- If it sees the same `scopeId` with different `css`, it throws a style conflict error.
- If the style is not present, it creates and appends a `<style data-s-id="...">` tag to
  `document.head`.

Hydration should therefore accept server-rendered style tags and avoid duplicating them.

## Compiler Integration

The compiler/Vite plugin should stop emitting direct DOM style insertion.

Instead, generated SFC code should call `useStyle(scopeId, scopedCss)` inside the component setup
path. That gives the same behavior in all three environments:

- Server render: collect the style.
- Hydration: detect the existing style tag and skip reinjection.
- Client-only mount: inject once into `document.head`.

No `.solace` syntax changes are needed.

## Error Handling

The first pass should fail loudly on conflicting style identity:

- Calling `useStyle()` outside an active render context should throw a clear runtime error.
- Re-registering a `scopeId` with different CSS should throw a style conflict error.
- Duplicate identical registrations should be ignored.

Silent best-effort merging is deferred because it can hide mismatched compiler output or
cross-request leakage.

## Package Boundary

The root package should export `useStyle` alongside the existing runtime helpers.

`@italone/solace/server` does not need a separate style API. The server renderer itself owns
collection; the runtime helper is the public registration point used by component code.

## Testing Strategy

Unit tests:

- `useStyle()` registers one style block during server rendering and returns one serialized
  `<style data-s-id="...">` entry.
- Duplicate identical registrations are deduped.
- Conflicting registrations with the same `scopeId` throw.
- `hydrate()` leaves an existing `style[data-s-id]` tag in place.
- `mount()` does not add a duplicate tag when the same style already exists.

Integration tests:

- Render an SFC or plain component that calls `useStyle()`, capture `renderToString().styles`,
  inject them into a jsdom document, hydrate, and verify no duplicate style tags appear.
- Render the same component without existing styles and verify client-only mount injects exactly
  one style tag.

Package tests:

- Update package export coverage to include `useStyle` on the root package.
- Extend packed-consumer smoke to import `useStyle` if the implementation exposes it publicly.

## Deferred Scope

- CSS modules.
- Style ordering beyond first encounter order.
- Automatic conflict resolution for different CSS with the same `scopeId`.
- Streaming SSR.
- Async component SSR.
- Router changes.
- SFC syntax expansion.
- Asset manifest integration.

## Risks

- If the compiler and runtime disagree on `scopeId` generation, hydration will either duplicate or
  reject styles.
- Global style caches can leak between requests if the collector is not request-scoped.
- Treating style tags as serialized HTML makes shell composition simple, but the shell must not try
  to reinterpret them as plain CSS.

## Acceptance Criteria

- Any component tree rendered through `renderToString()` can register styles through `useStyle()`.
- `renderToString().styles` includes the collected styles for that tree.
- Hydration reuses existing `style[data-s-id]` tags and does not inject duplicates.
- Client-only mount also dedupes by `data-s-id`.
- `.solace` output uses the shared runtime helper rather than direct DOM style insertion.
